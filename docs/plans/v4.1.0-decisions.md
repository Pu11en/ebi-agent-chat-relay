## D3: model-capacity-resilience (smallest readings of the spec)

- "Prompt or secure prompt reference" → the prompt text itself is stored in
  `capacity_pending_turns.prompt_ref` (same local SQLite trust boundary as
  `sessions`); it never reaches logs or the API (`RecoveryStatus.public_view`).
- A stopped turn (quota, login, exhausted, ambiguous) is *parked*: the row is
  rescheduled at its own `expires_at`, so it stays readable but is never due and
  `expire_before` retires it. The restart loader therefore only resumes turns that
  were genuinely mid-wait.
- Interactive fallback needs a `BackendFactory` to build the target's runner;
  without one (legacy embedded setups) the chain is ignored and the turn only
  waits. A fallback attempt starts a fresh session on the other CLI (session ids
  are not portable across backends), same as `/backend` mid-thread.
- `/gowork` builds keep their own build persistence (Q5 in the land-everything
  findings) and do not write `capacity_pending_turns`; they share the policy and
  the tracker (`RecoveryTracker`) through `_limit_hit`, and the build's
  `fallback_harness/fallback_model` is the one-entry `task`-authority chain.
- Non-retryable outcomes reach `/gowork`'s existing switch-or-wait question; auth
  failures now do too (they used to count as a failed try).
- Codex `input_tokens` includes cached tokens, Claude's excludes them. When the
  Codex runner folds `token_count` onto `turn.completed` it subtracts the cached
  part from `input` so the processor's `input + cache_read` sum is the real
  context size and the cache line stays visible (D10a).
- DSH windows are a prefix table (`MODEL_CONTEXT_WINDOWS`) with
  `CCDB_DSH_CONTEXT_WINDOW` overriding; the estimate counts the prompt as sent
  (standing instruction included) plus assistant text and reasoning, per session,
  and is labelled "(estimate)" via `context_label()` wherever a percentage is
  shown (D10b).
- T18: "every failure entry point shares the budget" names retries, smart_unstick, model escalation, splitting and goal-auto-round paths, which all belong to the legacy checkbox build → the manifest build has one automatic repair per task in the ledger (durable, one entry point); the checkbox build keeps its existing unstick ladder untouched → the two paths share no state (checkbox builds have no ledger), and rewriting the checkbox ladder onto the ledger is out of scope for a build that must keep old plan files working (Bootstrap Rules: compatibility includes old plan files and stored runs).
- D4: `openspec/changes/discord-command-surface/tasks.md` Check line named `tests/test_backend_command.py`, which does not exist (the `/switch` tests C1 cites are `tests/test_switch_command.py`) → the Check line now names `tests/test_switch_command.py` → a Check that cannot run proves nothing.

## D9: parallel-gowork (2.1, 4.3, 4.4, 5.1 metadata, 5.2)

- 4.3 “hard technical dependency makes independent planning unsafe” → a candidate `PlanDependency(kind=HARD, on=<active build id>)`; `ORDERING` and `SHARED_SCOPE` dependencies are carried into the child handoff instead → the spec names only a hard dependency as the refusal case, and the models already distinguish the three kinds.
- 4.3 explicit “make this separate” when the candidate would change the active build’s acceptance criteria → split anyway, with a reason telling the parent to revise its criteria → the spec lets only a hard dependency override an explicit request; the same goal as the active build still keeps together because a build cannot be split from itself.
- 4.3 “uncertain” → any of: goal reads like a phrase of the active goal (word subset or ≥60% overlap), no acceptance criteria, unknown whether it changes the active criteria, unknown writable scope, or overlapping writable scope; one question about the first doubt in that order → the spec asks for one focused question, not a checklist.
- 4.4 depends on 4.2 (planning registry), which C2 hands to T04 and which has no `ChildRecord` store yet → `planning_discord.py` takes a `ChildLedger` protocol (`get` / `put` / `children_of`) and a `PlanningTransport` protocol (spawn under a parent with a correlation ID, look a thread up by that ID, post) and ships `ApiPlanningTransport` over Ebi's localhost API → the adapter must not build the registry itself, and a narrow interface is what the design asked for.
- 4.4 “recovery must not create a duplicate child” after a spawn whose answer was lost → the record stays `creating` with no thread; the next request looks the split identity up as the spawn's `correlation_id` (5.1): found → attach, provably absent → create once, lookup failed → `blocked` for a person → same rule as the run-state ledger: uncertainty reconciles, never retries blind.
- 5.1 (metadata half) where the correlation/parent fields live → the existing `settings` key-value table (`thread_meta:<thread id>` JSON and `thread_correlation:<id>` → thread id) reached through `BridgeComponents.settings_repo`, not a new `sessions` column → no schema migration, `setup.py`/`api_server.py` edits stay additive, and the store is already opened for every deployment.
- 5.1 what a repeated `correlation_id` on `/api/spawn` does → 200 `{"status": "existing", thread_id…}` without spawning; `GET /api/correlations/<id>` is 404 when the identity was never recorded and 503 when no store is wired → a lost answer must be answerable without a second thread, and “nowhere to look” must never read as “provably absent” (the 4.4 adapter blocks on 503 and creates once on 404).


## D6: trusted-agent-handoffs

- 2.2: a handoff packet must fit one Discord message together with a short header (~1,100
  characters of goal + findings once the fixed fields are counted); a larger packet is refused
  at send time (`HandoffEnvelopeError`) rather than split across messages, because a starter
  that spans two messages cannot be found again by a reconnecting recipient. The protocol's
  6,000-byte bound stays as the transport-neutral limit.
- 3.1: `POST /api/project-lookup` used to let the runner's working directory beat
  `CCDB_PROJECT_LOOKUP_ROOT`; it now resolves through the same `lookup_root()` as the Discord
  path, so configuration wins and the working directory is only a fallback. The default lookup
  locator `drew/main-projects` is pinned to that root (not derived from an owner root), so the
  narrow slice keeps working with no new configuration; other locators need
  `CCDB_HANDOFF_PROJECT_ROOTS=owner=path,...`.
- 3.2: "materially unclear actions" is read as a keyword heuristic on the goal (open-ended
  phrases such as "whatever it takes", "full permissions", "etc."), erring toward blocking —
  a false positive costs one clarification in the job thread, a false negative would be an
  unapproved action. A packet that carries a capability the recipient policy forbids blocks
  visibly even when the goal never mentions it, instead of running a narrower task than asked.
- 3.3: the v1 packet has no session field, so "an explicitly named existing session" is an
  injectable `session_selector(task) -> thread id | None` on the executor; the shipped default
  returns `None`, i.e. every handoff runs as a fresh turn in its job thread. A restart resumes
  the interrupted attempt under the *same* attempt number (the claim row is closed as
  `interrupted` and reclaimed once) rather than spending a retry on the crash.
- 2.4: `on_ready` fires on every gateway reconnect, not only at startup, so the restart half of
  reconciliation (requeue `running` jobs) runs once per process while the starter scan runs on
  every reconnect — otherwise a job genuinely running in this process would be requeued
  underneath itself. Archived task threads are reached through the starter message (thread id
  == starter id) rather than a separate archived-thread walk.
- 4.2: each origin-facing message is posted by exactly one bot. The recipient delivers blockers
  and results to the origin conversation itself (outbox, retried — works while the origin bot is
  offline); the origin bot posts the acknowledgement and relays questions, and mirrors the rest
  into its ledger without a second copy. Clarification rounds (question/answer) are recorded but
  not acted on in v4.1.0: the packet is immutable, so an answer cannot change what a blocked
  job is allowed to do — a new task is the safe way to grant more.
