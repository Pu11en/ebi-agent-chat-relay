## D3: model-capacity-resilience (smallest readings of the spec)

- "Prompt or secure prompt reference" → the prompt text itself is stored in
  `capacity_pending_turns.prompt_ref` (same local SQLite trust boundary as
  `sessions`); it never reaches logs or the API (`RecoveryStatus.public_view`).
- A stopped turn (quota, login, exhausted, ambiguous) is *parked*: the row is
  rescheduled at its own `expires_at`, so it stays readable but is never due and
  `expire_before` retires it. The restart loader therefore only resumes turns that
  were genuinely mid-wait.
- Interactive fallback needs a `BackendFactory` to build the target's runner;
  without one (legacy embedded setups) the chain is ignored and the turn only
  waits. A fallback attempt starts a fresh session on the other CLI (session ids
  are not portable across backends), same as `/backend` mid-thread.
- `/gowork` builds keep their own build persistence (Q5 in the land-everything
  findings) and do not write `capacity_pending_turns`; they share the policy and
  the tracker (`RecoveryTracker`) through `_limit_hit`, and the build's
  `fallback_harness/fallback_model` is the one-entry `task`-authority chain.
- Non-retryable outcomes reach `/gowork`'s existing switch-or-wait question; auth
  failures now do too (they used to count as a failed try).
- Codex `input_tokens` includes cached tokens, Claude's excludes them. When the
  Codex runner folds `token_count` onto `turn.completed` it subtracts the cached
  part from `input` so the processor's `input + cache_read` sum is the real
  context size and the cache line stays visible (D10a).
- DSH windows are a prefix table (`MODEL_CONTEXT_WINDOWS`) with
  `CCDB_DSH_CONTEXT_WINDOW` overriding; the estimate counts the prompt as sent
  (standing instruction included) plus assistant text and reasoning, per session,
  and is labelled "(estimate)" via `context_label()` wherever a percentage is
  shown (D10b).
- T18: "every failure entry point shares the budget" names retries, smart_unstick, model escalation, splitting and goal-auto-round paths, which all belong to the legacy checkbox build → the manifest build has one automatic repair per task in the ledger (durable, one entry point); the checkbox build keeps its existing unstick ladder untouched → the two paths share no state (checkbox builds have no ledger), and rewriting the checkbox ladder onto the ledger is out of scope for a build that must keep old plan files working (Bootstrap Rules: compatibility includes old plan files and stored runs).
