## What's new (and how to try each one in 30 seconds)

### 1. Go Work runs a whole plan with many workers
**What it does.** You give `/gowork` a plan. Instead of one worker doing steps one after
another, the plan is split into tasks with owned files and dependencies; as many workers as
the machine can carry start at once (measured — not a fixed ten), each in its own thread and
its own copy of the project; results are merged one at a time, checked, reviewed, repaired
once if needed, and the finished build lands in the project by itself. If a worker gets stuck
it asks one question in Discord and you answer by replying to it. A bot restart picks up
where it left off without redoing finished work.
**Try it.** In a project control channel: `/gowork` with a plan that has a
` ```gowork-plan ` block (the planner writes one for you when you plan through the bot).
Watch the worker threads appear, one per task; reply directly to any "❓" question. Offline
preview without a bot: `uv run python -m claude_discord.gowork_demo`.

### 2. Capacity problems no longer dead-end a thread
**What it does.** "Model at capacity", quota, login and ambiguous provider errors are
recognised. The turn waits and retries with growing pauses, or moves to a fallback
backend/model if you configured one (`CCDB_CAPACITY_FALLBACK=codex:gpt-5.5,claude:sonnet`).
Stopped turns are parked and resumed after a restart. You see one live status line, not a
wall of errors.
**Try it.** Nothing to do — it is on by default. `GET /api/sessions` shows a
`capacity` block with `recovery` (phase, backend, timing; never the prompt).

### 3. Eight commands, one control row
**What it does.** The control channel's bottom row is now **status · New session · Sessions
· Settings**. *New session* offers Favorites, Recent, Browse, Projects (from the catalog),
Create and Clone. *Sessions* is a browser of your threads. *Settings* is a home screen other
features plug into. In a session thread, `/session` gives stop / clear / compact / goal /
rewind / fork / context as buttons; `/close` archives a thread (never deletes); `/help` only
shows what works where you typed it.
**Try it.** In the control channel press **New session → Favorites**, pick a folder, say
hello. In that thread type `/session`. Then `/close`.
The old commands still exist until Drew accepts the new ones live; then set
`CCDB_RETIRE_SUPERSEDED_COMMANDS=1` and restart to retire them.

### 4. One shared project catalog
**What it does.** Favorites, recents, hidden projects and "which computer has it" live in one
catalog keyed by owner and project — the launcher menus, the REST API and cross-computer
lookups all read the same list. A path is checked to be inside an approved root every time
before it is used.
**Try it.** **New session → Projects** lists the catalog; `curl -H "Authorization: Bearer
$CCDB_API_SECRET" "$CCDB_API_URL/api/projects?q=relay"` returns the same from the API.

### 5. Trusted bot-to-bot handoffs
**What it does.** DrewAI can hand David's bot (or the iMac's) a task: "look up project X",
"read these files and report". Off unless fully configured (`CCDB_AGENT_ID`,
`CCDB_HANDOFF_GUILD_ID`, `CCDB_HANDOFF_CHANNEL_ID`, `CCDB_HANDOFF_AGENTS`, plus
`CCDB_HANDOFF_TRUSTED_BOT_IDS`). A "read-only" packet runs a worker that *cannot* edit or run
shell — that is enforced in the command line, not just in the prompt. Progress, questions and
the result go back to the asking bot's thread, only inside the same server.
**Try it.** From DrewAI: ask it to "look up the ebi-agent-chat-relay project on David's
computer". A job thread appears on David's bot; the answer comes back in DrewAI's thread.

### 6. My AI Setup
**What it does.** **Settings → My AI Setup** shows what Claude Code, Codex, DSH and the
Discord extensions actually load on this computer — instructions, memory, skills, hooks, MCP
servers — where each lives, what changed recently, and a compare-with-another-computer view.
Every secret is redacted before anything is stored or shown. **Ask Setup Agent** opens one
session with a safe summary attached.
**Try it.** Control channel → **Settings → My AI Setup → Browse → Skills**.

### 7. Professional harness audit (command line)
**What it does.** `python -m extensions.harness_audit.cli audit --machine drewai --output
./audit-out` (add `--claude-home` / `--codex-home` if they are not under `~`) reads (never writes) your harness configuration, finds duplicates,
oversized files, wrong permissions, dead config and precedence problems, gives one verdict per
item (Keep / Fix / Move / Load-on-demand / Remove), compares machines, and can quarantine
files reversibly (`quarantine`, `rollback`) with hashes checked both ways. It refuses to
export a bundle that still contains a secret. Guide: `docs/harness-configuration-audit.md`.

### 8. Smaller things

  labelled as such).
- Feature-workflow extension: one branch + `.worktrees/wt-<thread>` per worker, child
  planning threads, `parent_thread_id` / `correlation_id` on `/api/spawn`.
- Automatic voice transcripts with speaker labels (`extensions/voice_transcripts/`, Node).
- Windows: the whole test suite passes on Windows; hidden bots no longer flash console

## Known issues / honest limits
- Go Work's real-model behaviour (does a worker follow its handoff?) is not measured offline;
  the practice run uses fake workers. First live build: watch it (`docs/gowork-upgrade-activation.md`).
- `edit_paths` in a handoff packet is advisory — the CLI can restrict tools, not paths.
- Check output relayed to Discord is not filtered (same trust level as the worker's reply).
- Very large manifests (thousands of tasks) re-read the ledger per access — fine for tens,
  not tuned for thousands.
- `extensions/harness_audit/sources.json` expires 2026-12-19; the CLI refuses to run after
  that until the manifest is refreshed.
- HTML/SVG preview rendering needs Chromium (Playwright); without it you get "no preview",
  which is the safe default.
